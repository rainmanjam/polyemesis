## Task 1: Fix the Windows test timeout before tagging

**This is the only thing blocking a release, and it is not a code bug.**

CI failed on the merge commit `db96946` with `panic: test timed out after 10m0s`.
Investigation showed it is runner variance, not a regression:

- `git diff bf01039 db96946` is **empty** — the merge commit's tree is identical
  to the branch tip that had passed Windows an hour earlier.
- Windows `internal/db` timings on that identical code: **264.8s** (passed),
  **297.2s** (passed on re-run), **>600s** (timed out).

`internal/db` uses `modernc.org/sqlite`, a pure-Go SQLite that is roughly 40×
slower on Windows than locally — 6.2s here, 265-300s there. It sits close enough
to Go's default 10-minute per-package timeout that ordinary runner variance flips
the build red.

Re-running turned it green, but "re-run it" is not a fix, and a suite that passes
on runner mood is not what to tag a first release against.

**The change:** give the test invocations explicit headroom in
`.github/workflows/ci.yml`, which currently sets no `-timeout` at all (lines 76
and 128), so Go's 10-minute default applies.

```yaml
# internal/db runs against pure-Go SQLite, which is ~40x slower on Windows than
# on a developer machine: 6s locally, 265-300s on a Windows runner, and once
# past 600s. Go's default per-package timeout is 10 minutes, so ordinary runner
# variance was enough to fail a build whose code had passed an hour earlier on
# an identical tree.
#
# 25m is roughly 5x the typical Windows run. It is not a licence for a slow
# suite -- it is headroom over a platform we do not control the speed of.
- run: go test -race -timeout 25m ./...
...
- run: go test -timeout 25m ./...
```

**Verify:** push, confirm the Windows job passes, and note the reported
`internal/db` duration so the headroom can be judged against reality.

## Task 3: Add the known limitations to the changelog

These are honest and worth stating in the release rather than discovered:

- **OAuth is optional and requires your own developer app.** Streaming works
  with a pasted URL and stream key on every platform. Connecting an account adds
  metadata push, chat, viewer stats and automatic stream-key fetch, and requires
  registering an application per platform. A guided setup that validates
  credentials at paste time is designed but not built —
  `docs/superpowers/specs/2026-07-30-guided-oauth-self-registration-design.md`.
- **A mistyped OAuth credential is not detected until you go live.** The
  consequence of the above.
- **The chat moderation UI has not been exercised end to end.** The Go and API
  layers are unit- and mutation-tested; the browser click-through needs a
  connected platform account, which the acceptance suite cannot supply.
- **Facebook requires App Review before anyone but you can connect.** Meta's
  process, not something polyemesis can shorten.

## Deferred: OAuth

Two designs are committed and reviewed, and neither is started beyond the
foundation:

- `docs/superpowers/specs/2026-07-30-guided-oauth-self-registration-design.md`
  — validate credentials at paste time, warn about an unusable redirect URI.
- `docs/superpowers/specs/2026-07-30-oauth-broker-design.md` — a hosted broker
  modelled on OBS Studio's `auth.obsproject.com`, so self-hosters register
  nothing for Twitch, Kick and Facebook. YouTube is permanently excluded on
  quota grounds; the arithmetic is in that document.

Partial work sits on the branch `worktree-oauth-self-registration` in
`.claude/worktrees/oauth-self-registration`: Tasks 1-2 of the implementation
plan, commits `cd829cf..992b49b`. It is **not** merged and should not be —
nothing is wired to the API yet, so it would add unused exported functions.
Resume by re-reviewing `80a6e77..992b49b` and continuing at Task 3 of
`docs/superpowers/plans/2026-07-30-guided-oauth-self-registration.md`.

  signature verification with a public key — no decryption oracle exists — and
  the padding scheme is Kick's choice, not ours. Analysis in

  convenient.
